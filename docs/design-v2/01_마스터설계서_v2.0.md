### 1. Claude 중심 개발 환경 \[유지 + 보완\]

코드는 Claude가 쓰고, 실행·테스트는 Replit Shell에서 사용자가 합니다. Replit Agent는 쓰지 않습니다(크레딧 절약).

| 작업 | 어디서 | 누가 | 비고 |
| --- | --- | --- | --- |
| 설계, 코드 작성, 오류 수정, 코드 리뷰 | Claude 대화 | Claude | 단계 브랜치에 커밋 |
| 기획 보조, 코드·SQL 교차 검토, 제출자료 | ChatGPT 대화 | 사용자 + ChatGPT | 10/21 STEP 3-B 원인 분석, STEP 3-C SQL 검토에 실제 활용 |
| 코드 저장·이력 | GitHub `safe-school`(비공개) | Claude가 올리고 사용자가 확인 | 단계마다 브랜치 보존 |
| 설치·실행·테스트 | Replit Shell | 사용자 | 출력 전체를 Claude에 전달 |
| 미리보기·시연 | Replit Run(Webview) | 사용자 | 시연 스키마 `safeschool_browser_demo` |
| 실제 운영 주소 | Replit Deployments | 사용자 | 아직 배포 안 함(배포 단계에서) |

**Claude 작업공간에서 할 수 있는 것(10/20\~21 확인)**: npm 패키지 설치는 막혀 있지만 PostgreSQL·Node.js·Chromium은 있어, 마이그레이션 SQL 적용, DB 제약 점검, 순수 함수 테스트, 모의 서버 브라우저 검사까지는 Claude가 먼저 합니다. 실제 Prisma·Express 실행이 필요한 `npm test`와 e2e는 Replit 결과로만 '검증 완료'를 표시합니다.

**Replit 비용을 아끼는 규칙**

1. Agent 칸에는 아무것도 입력하지 않습니다. 오류 수정도 Claude에게 맡깁니다.
2. Replit에서 코드를 직접 고치지 않습니다. 예외는 Replit이 만드는 `package-lock.json`·`.replit`·워크플로 설정이며, 이 파일은 Replit 로컬 브랜치에서만 관리합니다. **\[개정\]**
3. 개발 중에는 Run(미리보기)만 씁니다. Deploy는 배포 단계(원본 STEP 7)와 실증 직전에만 합니다.
4. 원본 시점의 빈 Replit 앱(AffectionateApprehensiveConfigfiles)은 사용하지 않습니다.

코드는 Claude → GitHub → Replit 한 방향으로 흐르는 원칙을 유지합니다. 바뀐 점은 Replit 쪽 반영 방식입니다.

**단계마다 반복할 일(현재)**

1. Claude가 단계 브랜치에 코드를 올리고, 바뀐 파일과 실행할 명령을 알려 줍니다.
2. 사용자가 Replit Shell에서 백업 브랜치를 만든 뒤 병합합니다.
3. `npm run db:generate` → `npm run typecheck` → `npm test` → `npm run e2e:step2` → `npm run e2e:step3` → `npm run e2e:step3b` 순서로 실행하고 출력 전체를 Claude에게 보냅니다.
4. 새 마이그레이션은 **테스트 스키마에서 먼저**, 통과 후 **사용자 승인을 받아** 시연 스키마에 적용합니다.
5. 결과는 `docs/test-record.md`와 포트폴리오 일일 기록에 남깁니다.

### 3. 기존 프로젝트 코드 확인 절차 \[유지\]

읽기 전용 확인 → DB 백업(`npm run db:backup`) → '보존 / 수정 / 교체' 판정 → 사용자 승인 순서를 유지합니다. 승인 전에는 어떤 파일이나 데이터도 삭제하지 않습니다. 원본 시점 적용 결과(빈 템플릿이라 새 저장소로 시작)는 I절에 보존했습니다.

### 4. 전체 시스템 아키텍처(요약 → B절) \[개정\]

교직원의 휴대폰·PC 브라우저가 Replit의 서버 하나(Express 5)에 접속하고, 서버가 화면(React 19)과 API를 함께 제공하며 PostgreSQL(Prisma 6)에 저장합니다. 모든 학교 업무 API는 '로그인 → 승인된 소속 → 역할 → 학교 범위' 검사를 거칩니다. 외부 서비스(메일, 학교알리미, 재난경보 공급자)는 어댑터로 분리되어 장애가 나도 발령·보고·집계는 멈추지 않습니다. **학부모는 현재 앱의 사용자가 아닙니다**(학부모 안내는 교사가 학교 기존 채널로 발송).

- 가입·승인 업무가 새로 생깁니다. 학기 초 1회, 관리자 일괄 승인으로 줄입니다.
- 보고서를 학교안전지원시스템에 다시 입력해야 할 수 있습니다. 3-D에서 실제 제출 서식 순서에 맞춥니다(서식 필요).
- **\[추가\]** 안내문을 앱에서 쓰고도 결재 시스템에 다시 붙여넣어야 합니다. 그래서 앱 내 결재를 두지 않고 복사 한 번으로 끝나게 했습니다.
- **\[추가\]** 경보함이 기존 재난문자와 같은 내용을 반복하면 확인 업무만 늘 수 있습니다. 학교 대상 경보만 보이고 재송출은 한 건으로 묶습니다.

**요청이 지나는 순서(서버)**

1. JSON 본문 검사·크기 제한(100kb), 상태 변경 요청의 CSRF 대응(JSON만 허용 또는 전용 헤더)
2. 세션 쿠키 확인 → 기기 종류별 만료·미사용 만료 검사
3. 학교 API는 `schoolId`로 소속 조회 → 승인 상태 → 역할 → 학교 활성 상태 검사(다른 학교는 404)
4. 업무 처리와 같은 트랜잭션에서 감사 로그 기록
5. 오류는 `{ code, message }` 형식으로 통일

## E. 백엔드 API 목록

실제 코드에는 API 34개가 있습니다(health 1, auth 7, schools 14, events 8, alerts 4 — 아래 표로 확인). 원본은 `/api/members`처럼 학교 없는 경로였지만, 실제는 모두 `/api/schools/:schoolId/...`로 학교를 경로에 넣고 서버가 소속을 다시 검사합니다. 구현하지 않은 API는 '미구현'으로 적었습니다.

공통(원본 유지·수정): 오류는 `{ code, message }`, 401 미로그인, 403 권한 없음·미승인, 404 없음·다른 학교, 409 중복 발령·버전 충돌·종료된 상황, 422 합계 불일치, 429 요청 과다. CSRF는 원본의 토큰 방식 대신 'JSON 본문만 허용 + 본문 없는 요청은 전용 헤더'로 구현했습니다. 멱등키는 학급 보고에만 필수입니다(원본은 발령·발송에도 계획).

## F. 외부 플랫폼 연동 가능성과 제약

현재 실제로 동작하는 외부 연동은 학교알리미 OpenAPI(학교 검색·기본정보)와 메일 발송 어댑터 두 가지이고, 둘 다 실제 서비스로는 일부만 확인했습니다. 공식 재난경보는 모의 공급자로만 검증했습니다. 원본이 검토한 대상은 모두 남기고, 세 단계로 다시 나눴습니다. 공식 접근 권한이나 계약이 없는 기능은 '연동 가능'으로 쓰지 않습니다.

### K-3. STEP 3-C 재난안전 안내문 작성 지원 및 교사 직접 발송 — 설계 확정·개발 중

**개발 배경과 설계 변경 이유**: 원본은 관리자가 학부모 안내문을 작성·승인하고 웹 푸시 또는 모의 발송하는 구조였습니다. 실제 학교에서는 K-에듀파인 등 기존 공문 결재 절차를 거친 뒤 담당 교사가 학교가 쓰는 별도 채널로 안내문을 보냅니다. 사용자의 현장 경험에 따라 앱 내 관리자 결재와 앱 내 발송을 제거했습니다. **기능 축소가 아니라 결재·발송의 중복 업무를 없애기 위한 설계 변경**입니다.

**최종 기능 범위(12개)**

1. STEP 3-B 재난경보함에서 안내문 작성 화면으로 연결
2. 재난 유형별 안내문 예시 제공
3. 예시문 선택 시 편집 영역으로 불러오기
4. 기존 작성 내용이 있으면 덮어쓰기 확인
5. 학교명·경보 유형·지역·발령 시각 등 확인 가능한 정보 자동 입력
6. 교직원이 제목·본문을 자유롭게 수정
7. 안내문 저장과 판 번호 관리
8. 이전 수정 이력 보존
9. 제목 복사·본문 복사·전체 복사
10. 안내문 미리보기
11. 선택적 처리 이력 기록
12. 학교별 데이터 격리와 작성 권한 관리

**예시문 구성(21개)**: 재난 유형 7종(폭염, 호우·태풍, 미세먼지, 지진, 한파, 화재·가스, 기타) × 상황 3종(학부모 발령 안내, 교직원 발령 안내, 해제 또는 상황 종료·안전 확인 안내). 예시문 원본은 코드 데이터(`shared/noticeExamples.ts`)로만 두어 화면·DB에서 바꿀 수 없고, 교사가 고친 글만 `school_notices`에 저장합니다. 저장된 안내문에는 불러온 예시의 키·버전을 남깁니다.

| --- | --- |

**선택적 업무 처리 이력**: 작성 완료 여부(상태 '작성 완료'), 교사가 이용한 발송 채널 종류(문자 / 학교 알림 앱 / 카카오톡 / 기타, 기록용 분류), 발송 대상 범주, 교사가 직접 입력한 발송 여부·시각, 비고. 이 기록은 교직원의 입력이며 **실제 외부 발송 성공이나 공식 결재 완료를 증명하지 않습니다.** 화면에도 그렇게 안내합니다.

**DB 설계(`step-3c-notices` 브랜치 SQL 2차)**: `school_notices`, `school_notice_revisions`, `notice_handling_records` 3개 테이블. 학교와 연결 경보의 소속 일치(복합 외래키 + 생성 시 대상·대표 경보 검사), 취소 후 수정 방지, 수정 이력 DB 자동 보존(판 번호 +1 강제), 동시 수정 방지(조건부 갱신 + 판 번호)를 유지합니다. 작업공간 점검 35/35. **시연용 DB에 적용하기 전에는 반드시 별도 승인을 받습니다.**

### L-5. 자유 의견·개선 요구와 재테스트(원본 C 보존)

서술 문항 5개(가장 편했던 기능, 불편했던 화면, 없어진 일과 새로 생긴 일, 실제 재난 때 쓰지 못할 이유, 꼭 바뀌었으면 하는 점)를 받고, 모든 의견을 개선 목록(번호·역할·기능·원문·심각도·조치·상태·재테스트 결과)으로 옮깁니다. 심각도 상(보고 실패·잘못된 숫자)·중(업무 증가·혼란)·하(표현·배치). 2명 이상 지적 또는 평균 3.5점 미만이면 우선순위를 한 단계 올립니다. '상'은 제출 전 반드시 고치고, 지적한 사람이 같은 과제로 재테스트합니다.

### L-6. 기존 방식 대비 소요시간 측정(원본 D 보존)

같은 가상 상황 카드(예: 지진 훈련, 6개 학급, 결석 2·미확인 1·부상 1)로 A안(기존: 메신저·전화 보고, 종이 집계, 안내문 직접 작성, 한글 결과보고)과 B안(SAFE SCHOOL)을 재현합니다. 숫자를 바꾼 2세트로 순서 효과를 줄이고(가능하면 절반 A→B, 절반 B→A), 구간별로 ① 발령→전 학급 보고 완료 ② 보고 완료→집계 확정 ③ 확정(또는 경보 수신)→안내문 완성 ④ 종료→결과보고 초안 완성을 잽니다. A안은 스톱워치, B안은 감사 로그 시각. 결과는 '모의 측정치'로 표기하며 실제 재난의 시간 단축을 입증한 것으로 쓰지 않습니다. **\[개정\]** ③ 구간의 B안은 '승인 1회'가 아니라 '예시 불러오기·수정·복사'로 잽니다.

### L-7. 결과 분석과 제출 증빙 구조(원본 E·F 보존)

표본 5\~10명이라 통계적 유의성은 주장하지 않고, 평균과 함께 최솟값·최댓값·응답자 수를 적습니다. 증빙은 파일 하나로 냅니다(원본 기준, 공고문 재확인). 순서: ① 실증 요약 ② 업무 절차 비교표 ③ 탁상 비교 측정 기록지 ④ 모의훈련 앱 기록(감사 로그·보고서, 학생 실명 없음) ⑤ 사용성 테스트 결과 ⑥ 사용자 평가 결과 ⑦ 담당자 후기 원문(서명·동의) ⑧ 개선 이력 ⑨ AI 협업 기록 ⑩ 보안·데이터 관리 ⑪ 사용 현황. 각 자료에 '측정 / 모의 측정 / 사용자 인식 / 추정' 라벨을 붙입니다.
