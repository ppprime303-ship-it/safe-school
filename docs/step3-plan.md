## 3. STEP 3-A 구현 순서

1. **A1 발령**: 관리자만. 훈련이 기본값이고, 실제 상황은 `confirmReal: true`가 있어야 발령. 학교당 진행 중 1건(DB 부분 UNIQUE)이며, 동시 발령 시 두 번째 요청은 409와 함께 기존 사건 ID를 돌려줌. 복합재난은 유형 추가. 대피 장소·안내 수정.
2. **A2 보고**: 담당 학급(담임·보조 배정) 또는 관리자(대리, 사유 기록). 멱등키 필수, 버전 충돌 409, 미확인은 서버가 계산, 재적 변경 사유 검사. 종료된 사건에는 보고 불가.
3. **A3 상황판·종료**: 관리자만. 서버 시각 포함, 학급별 최신 보고와 미보고 구분. 종료는 실제 상황이면 `confirmClose: true` 필요. 종료 시 최종 집계를 감사 로그에 남김(보고서 초안의 근거).
4. **A4 검증**: 서비스 DB 테스트(vitest), 2개 학교·2개 역할 E2E 스크립트(`npm run e2e:step3`), 화면 연결.

## 4. API 계약(STEP 3-A)

모든 경로는 `/api/schools/:schoolId/events…`이며, 서버가 소속·승인·역할·학교 활성 상태를 검사한다(다른 학교는 404).

| 메서드·경로 | 권한 | 요청 | 응답 |
| --- | --- | --- | --- |
| GET `/events/active` | 승인된 교직원 | – | `{ event: ActiveEvent \| null }` |
| POST `/events` | 관리자 | `{ primaryType, mode, location?, evacPlace?, message?, confirmReal? }` | 201 `{ event }` / 409 `event_already_active` |
| POST `/events/:id/types` | 관리자 | `{ type, note? }` | `{ event }` |
| PATCH `/events/:id` | 관리자 | `{ location?, evacPlace?, message? }` | `{ event }` |
| GET `/events/:id/board` | 관리자 | – | `BoardData { event, serverTime, classes[] }` |
| GET `/events/:id/my-classes` | 승인된 교직원(관리자는 전체) | – | `{ classes: ClassReportView[] }` |
| PUT `/events/:id/reports/:classId` | 배정 교직원·관리자 | 헤더 `Idempotency-Key`, 본문 `ReportInput` | `{ report }` / 409 `version_conflict`·`event_closed` / 422 `sum_mismatch` |
| POST `/events/:id/close` | 관리자 | `{ confirmClose? }` | `{ event, summary }` |

형식은 `client/src/lib/disaster.ts`의 타입과 같다. 학생 이름 등 개인 식별정보는 받지 않는다(메모에도 금지 안내).

## 5. 보안 설계

- 권한은 화면이 아니라 서버에서 `resolveSchoolAccess`(STEP 2)로 검사한다. 보고 권한은 '배정된 학급' 단위로 확인한다.
- 실제 상황 발령·종료는 요청 본문의 명시적 확인 플래그와 화면의 확인 문구 입력을 둘 다 요구한다.
- 멱등키로 재전송 중복을 막고, 버전으로 동시 수정 덮어쓰기를 막는다.
- 모든 발령·유형 추가·수정·보고·종료를 감사 로그(추가만 가능)에 남긴다.
- 학교 재난 발령은 사람이 결정한다. 공식 경보 수신만으로 자동 발령하지 않는다(3-B).

## 6. STEP 3-B 공식 경보·학부모 전달: 구현 가능성과 미확인 사항

**확인한 사실**
- 행정안전부 긴급재난문자는 재난안전데이터 공유플랫폼에 등록되어 있다(dataSn=228). 회원가입과 활용 신청이 필요하고, 응답은 JSON/XML이다.
- 공공데이터포털에도 등록되어 있다(15134001). 갱신주기는 실시간이고, 개발 단계는 자동승인, 운영 단계는 심의승인이다. 이용허락은 **공공누리 제4유형(출처표시·상업적 이용금지·변경금지)** 이다. 원문을 고치지 않고 학교 안내를 따로 붙이는 설계는 이 조건과 맞는다.

**확인 필요**
- 요청 주소, 서비스 ID(인수인계 문서의 `/V2/api/DSSP-IF-00247`), 응답 필드명, 호출 제한, 지연은 두 공개 페이지에서 확인하지 못했다. 활용 신청 후 이용가이드를 받아야 한다.
- 지역 표기 방식(시군구 이름 문자열인지 코드인지), 정정·취소 문자 표현, 같은 문자의 재송출 식별 방법.
- 기상특보·미세먼지 등 환경 경보는 출처·심각도·기간 체계가 달라 공급자별 어댑터로 따로 검증해야 한다.
- 학부모 실발송: 연락처 수집 근거·동의, 발송 공급자(문자·알림톡·웹푸시) 계약, 비용, 학교 승인. 현재 학부모 연락처·발송 채널 기능은 없다.

**설계 [설계]**
- 공급자 어댑터를 `fetchSince(cursor) → OfficialAlert[]` 인터페이스로 두고, 먼저 모의 공급자만 연결한다. 실제 공급자는 키와 필드를 확인한 뒤 추가하고 기본은 꺼 둔다.
- 데이터는 다음 표로 나눈다.
  - `official_alerts`: 원문, 발령기관, 발령·수신 시각, 원본 ID를 저장한다. 수정·삭제는 트리거로 거부한다.
  - `school_alert_matches`: 대상 / 비대상 / **미판정**을 기록한다. 학교 지역이 불명확하면 미판정으로 둔다.
  - `school_alert_notices`: 학교 보충 안내를 원문과 분리해 담고, 작성·승인·수정 이력을 남긴다.
  - `alert_dispatches`: 대상(교직원/학부모), 채널(앱 내/모의), 상태(대기·성공·실패·미발송·중복 억제)를 기록한다. (원본 경보, 대상, 수신자) 조합이 같으면 다시 만들지 않는다.
  - `school_alert_policies`: 기본값은 앱 내 교직원 게시만 켜고, 외부 발송은 끄고, 승인을 필수로 한다.
- 지역 필터를 위해 학교 소재 시도·시군구 정보가 필요하다. 학교알리미 주소에서 추출한 값을 관리자가 확인하는 방식으로 한다.

## 7. STEP 3-C 보고 지원

- **[매뉴얼]** 학교안전사고: 인지 즉시 유선 보고, 사고 발생 24시간 이내 공문 보고, 상황 변동 시 추가 보고(제2편). 재난: 최초·경과·복구 보고(제4편).
- **[설계]** 사건 타임라인을 한 번 입력하면 원인·피해·조치·경과 보고 초안을 만들고, 24시간 기한을 안내하고, 변경분을 추적한다. 공문 발송과 유선 신고는 앱이 대신하지 않는다.
- **[확인 필요]** 매뉴얼은 경기도교육청 맥락이다. 인천 등 해당 시도교육청의 보고 기한·서식·경로는 정책 설정에 '확인 필요'로 남기고, 운영자 확인 후 반영한다.

## 8. 구현 전 사용자 확인이 필요한 정책

경보 유형별 알림 대상과 즉시 전송 여부, 승인 권한자, 공식 발송 채널, 학부모 연락처·동의 관리, 학교별 보고 양식, 해당 시도교육청 기준, 기존 시스템 데이터 반입 경로.
