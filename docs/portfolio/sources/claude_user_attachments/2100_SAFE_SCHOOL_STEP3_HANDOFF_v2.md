## 03. DB·Replit 현황과 안전 규칙

PostgreSQL DB명 heliumdb. 스키마 public(기본/운영용, 초기 마이그레이션 미적용으로 확인됨), safeschool_test(자동 테스트; 테스트 시 데이터 초기화), safeschool_browser_demo(실제 브라우저 시연; 두 마이그레이션 적용/가상 데이터 존재). 실제 브라우저 서버는 마지막에 다음 명령으로 실행: DATABASE_URL="$(node -e 'const u=new URL(process.env.DATABASE_URL);u.searchParams.set("schema","safeschool_browser_demo");process.stdout.write(u.toString())')" MAIL_PROVIDER=console NODE_ENV=development npm run dev
학교알리미 키 SCHOOLINFO_API_KEY 미설정. 시연 학교는 school_directory_entries에만 가상 schoolinfo source, externalCode SAFE-DEMO-001로 주입하여 시작. 실제 학교 공식 데이터로 오해/배포하지 말 것.
테스트 계정은 teacher01@example.com(가상 관리자), teacher02@example.com(가상 담임)이며 비밀번호, 인증코드, Secret은 문서에 저장하지 않는다. 최초 가상 등록 승인은 시연용 메모로만 표시.
기존 사용 데이터 보존. prisma migrate reset / db push --force-reset / TRUNCATE public / 실데이터 덮어쓰기 금지. 새 마이그레이션은 비파괴적 검토 후 테스트 스키마에서 선검증. E2E는 safeschool_test를 초기화하니 브라우저 시연 스키마와 혼용 금지. 현 Replit에서는 npm v11.11.0을 npx로 사용해 npm install 성공했던 이력. package-lock.json GitHub 반영 여부 확인.

## 05. STEP 3 개발 범위 A — 발령·대피·상황판

우선순위 A1: 관리자 전용 훈련/실제 재난 발령, 유형(지진/화재/폭염/호우 등), 대피 장소/시간/메시지, 실제 상황 명시적 확인, 학교당 활성 1건/복합재난/동시성 처리. 학교·교육청 지침과 맞출 것.
A2: 담임교사 로그인 후 승인된 담당 학급+재적 자동 로딩; 단일 배정이면 선택 단계 없이 바로 보고. 전원 대피 확인 버튼, 부분 대피 인원/미확인 자동 계산, 사전 파악 부재·부상·메모 접기, 학생 식별정보 불필요. 저장 결과/미전송 명확히 구분, 재시도·멱등성·충돌 버전 처리.
A3: 관리자 상황판 5초 갱신/미보고 별도 표시, 재적 기준 학급별·전체 대피/부재/미확인/부상 집계, 마지막 갱신시각과 통신 오류 표시, 갱신 실패 시 이전 값을 실시간 데이터처럼 오인시키지 않음. 학교별 권한/감사 로그. 실제 종료 명시적 확인/최종 스냅샷/보고서 기반 데이터 보존.
A4: API 스펙 작성, Zod 검증, DB 제약, 실제 서버 E2E/프런트 통합 검증, Replit에 검증 명령 1~3개씩 제공.

## 06. 신규 필수 요구 — 국가 재난경보 자동 연동과 학교 맞춤 추가 안내

현장 문제: 환경/기상/국가 재난경보 발생 때마다 교사가 교직원·학부모에 수기로 전파해야 하는 부담. 목표는 공식 경보의 중복 입력을 없애고, 학교 맥락에 맞는 추가 안내도 한 번에 처리하는 것.
공식 후보: 재난안전데이터 공유플랫폼의 행정안전부_긴급재난문자(데이터 상세 dataSn=228, REST /V2/api/DSSP-IF-00247, 갱신주기 안내 1분; 이용신청 필요). 출처: https://www.safetydata.go.kr/disaster-data/view?dataSn=228 . 실제 API 키, 필드·호출 제한·지연, 지역 코드·경보 변경·취소·반복, 이용허락/문자 재전송 조건 확인 후 구현. 재난문자와 기상특보·미세먼지 등 환경 경보는 출처/심각도/기간이 다르므로 경보원별 어댑터로 별도 검증. 현 단계에서 모두 지원된다고 주장 금지.
알림 분리: (1) 공식 경보 수집/필터링(학교 소재지·관할·심각도, 중복 제거 및 원문/발령기관/발령시각/수신시각/원본 식별자 저장), (2) 앱 내 자동 게시·교직원 알림, (3) 학부모/교직원 외부 알림 발송. 이 셋을 독립 정책으로 설정하며, 출처가 지연되거나 API 오류면 '연동 지연/수동 운영 절차' 명시. '즉시 전달' 무보증.
학교 관리자 설정: 재난 유형/위험도/관할에 따른 자동 알림 대상과 채널, 조용한 시간 예외/중복 억제, 테스트/실제 분리; 긴급도 높은 경보에 대해 사전 승인된 알림 규칙의 자동 발송은 가능하도록 설계하되 초기 기본값은 실수 발송을 막는 안전한 설정으로 시작. 중요한 재난은 담당자 확인을 거치도록 옵션화하고, 자동 발송 여부와 승인을 운영자 정책으로 구분. 공식 경보 원문은 수정 금지; 학교 보충 안내를 별도 필드로 입력해 원문 아래 추가, 출처/학교 작성자/시각을 구별해 보여주기. 학교장/지정 담당자만 공개 발송 권한.
교직원/학부모 구분: 실제 외부 전송은 학교가 제공/승인한 연락처·동의·개인정보 처리·인증된 채널이 있어야 함. 현재 STEP 2에는 학부모 연락처/발송 채널/동의관리 등이 구축된 것으로 확인되지 않았으므로 실제 전송을 가동했다고 주장할 수 없음. P0는 가상 수신자+모의 발송 및 앱 내 알림, P1은 승인된 메시징 공급자 어댑터(카카오 알림톡·SMS·웹푸시 등 가능성 검토)와 전송상태/재시도/템플릿/비용, P2는 수신자 관리·대상별 동의 및 보관기간/탈퇴 처리. 학교별 접근·수신자 최소정보·감사로그·전송 실패 확인/수동 대체 경로.
재난문자 수신은 학교 재난 발령과 동일 개념이 아님: 공식 경보 자동 수신만으로 학교 내 대피 발령을 자동 개시하지 말고, 위험도 및 관리자 승인 정책을 별도 설계할 것. 학교장/학교 안전담당자가 경보에 '오늘은 실외활동 중단, 하교 계획 추후 공지' 등 보충 문구를 덧붙여 1회 작성으로 정해진 수신 대상에 송신할 수 있게. 재전송/수정/취소 내역과 누가 언제 알렸는지 기록.

## 07. STEP 3 통과 기준(DoD)

① 실제 훈련 발령→담임 자동 학급·재적 표시→대피보고→상황판 수치 일치→종료까지 2개 학교/2개 역할 E2E. ② 동시 발령/중복 보고/수정 버전 충돌/권한 차단/통신 끊김 재시도/감사로그 테스트. ③ 공식 경보 연동은 API 접근권·응답 필드 확인 전에는 mock adapter로만 통합 테스트하고 실제 연동 완료라 표시하지 않음. ④ 경보의 학교 지역 필터·중복 제거·학교 보충 안내 작성·학부모/교직원 대상 구분·모의 전송/전송 상태 테스트. ⑤ UI는 모바일 포함, 강한 대비와 48px 터치영역, 빠른 조작/중복 입력 없음. ⑥ npm run typecheck, npm test, npm audit, Step3 E2E 결과를 실제 실행 출력으로 문서 갱신. ⑦ Replit 브라우저 기능 테스트는 safeschool_browser_demo 같은 시연 스키마에서, 기존 데이터 보존. ⑧ 새 기능의 완성/미완성·제약을 README/docs/test-record.md에 분리 기록.

### 09.2 STEP3 백로그 편성(범위 통제)
- STEP3-A(필수 완료): 학교 관리자 재난 훈련/실제 발령(분명한 구분), 담당 학급 자동 조회·재적/보고, 실시간 상황판·미보고/미확인 집계, 상황 종료 및 사건 타임라인/보고서 초안. 기존 UI 및 재난 DB 스키마를 재사용.
- STEP3-B(필수 최소 구현): 경보 수집 인터페이스 + 검증 가능한 모의 공급자, 지역 필터/원본 저장/중복 제거, 앱 내 교직원 경보 화면, 공식 원문 아래 학교 별도 보충 안내, 승인 로그 및 가상 대상 모의 발송/전달 상태. 실 API와 실제 외부 발송은 키·동의·계약·학교 승인 전까지 비활성.
- STEP3-C(최소 구현 권장): 사고·재난 사건 타임라인에서 1회 입력으로 보고 초안 생성(원인/피해/조치/경과), '즉시 유선 보고 필요'와 '24시간 이내 공문' 등 매뉴얼상의 확인 항목 안내; 원클릭 공식 전송 금지.
- STEP4: 안전교육 7대 영역·실적/이수·서식, 기한 캘린더.
- STEP5: 시설 안전점검의 날, 현장체험학습 사전점검, 조치 이력.
- 구현 전 사용자 확인이 필요한 정책: 경보 유형별 알림 대상/즉시 전송 여부, 승인권한, 공식 발송 채널, 학부모 연락처·동의 관리, 학교별 보고 양식, 기존 시스템 데이터 반입 경로.

### 09.3 자동화 기본 설계 원칙
1. 사건 ID를 중심으로 '경보 → 학교 의사결정 → 내부 알림 → 조치 → 대피 보고 → 교육청 보고서 초안'을 연결하고 재입력을 줄인다.
2. 공식 경보와 학교 자체 문구는 작성 주체·시각·내용을 분리해 변경 내역 보존. 과거 원문을 덮어쓰지 않는다.
3. 정상 수신·전달 성공·읽음·미확인·실패를 혼동하지 않는다. 재발송은 동일 원본 경보와 수신자 기준으로 중복 억제한다.
4. 기한 자동 알림은 정해진 기준과 시간대(Asia/Seoul)를 바탕으로 하되, 매뉴얼 조항/시도별 예외는 버전 관리하고 운영자 확인을 요구한다.
5. 위험도 자동 분류는 참고용이며 학교장의 휴업/단축수업, 실제 대피 발령, 유선 신고, 공문 제출을 자동 결정하지 않는다.
6. 학생 개인 식별·건강정보는 기본 보고 화면에서 수집하지 않는다. 개인정보 보존·삭제·학교별 접근제어·감사로그를 정의한다.
7. 타 시스템으로 강제 이중 입력을 만들지 않는다. 표준 서식 출력/승인된 내보내기를 우선하고 공식 API 연계는 권한 확인 후 검토한다.

### 09.4 추가 인수인계 완료 조건과 테스트 시나리오
- [ ] 외부 경보 원본 1건 수집 시 중복 폴링해도 경보와 대상별 알림이 중복 생성되지 않는다.
- [ ] 인천 관련 경보는 인천 시연 학교에, 다른 지역 경보는 비대상 학교에 잘못 전달되지 않는다(행정구역 불명 시 안전한 미판정 처리).
- [ ] 국가 경보 표시만으로 학교의 재난 발령/휴업 결정이 자동 처리되지 않는다.
- [ ] 학교 보충 안내가 원문과 분리되어 표시되며 작성·승인·수정 이력이 남는다.
- [ ] 가상 학부모/교직원 대상 모의 전송에서 성공/실패/미발송/중복 억제를 구분한다. 실제 발송은 기본 비활성.
- [ ] 사고 발생 24시간 내 공문 보고 체크/알림과 상황 변경 추가 보고 초안이 동작한다(단, 자동 공문 발송은 없음).
- [ ] 기존 52개 자동 테스트와 STEP2 E2E 40개가 회귀 없이 통과하고, 새 STEP3 E2E가 재난 발령→보고→집계→종료를 통과한다.
- [ ] 매뉴얼 기준과 실제 해당 시도교육청 기준의 차이를 식별해 정책 설정 화면 또는 문서에 기록한다.

### 09.5 참고 출처와 추론 구분
- [매뉴얼 직접 기재] 제1편: 학생·교직원 안전교육 실적 보고 연 2회(8월, 12월). 제2편: 학교안전사고 인지 즉시 유선 보고, 사고 발생 24시간 이내 공문 보고, 상황 변동 시 추가 보고. 제4편: 재난상황 최초/경과/복구 보고 절차, 기상/환경 재난별 대응. 제5편: 안전점검의 날 매월 4일 원칙(학교 실정에 따라 변경 가능).
- [설계 제안] 체크리스트 자동화, 알림 메시지 승인/발송 이력, 24시간 타이머, 모바일 점검 기록, 서식 자동화, 교육실적 대시보드는 매뉴얼에 앱 기능으로 규정된 내용이 아니라 이 매뉴얼 업무를 경감하기 위한 제안이다.
- [미확인/외부 의존] 행안부/기상청/환경부 실 API 사용 권한과 데이터 스키마, 실제 메시징 제공자, 학부모 연락처·동의 확보, 인천교육청 적용 기준은 별도 확인 필요.
