# STEP 6 심사위원 시연 데이터 계획

도구: `scripts/judge-demo-setup.ts`(`npm run judge:setup`), 계획 로직: `server/src/deploy/judgeDemo.ts`
**아직 어느 DB에도 실행하지 않았습니다.** 국내 VPS의 `safeschool_prod_judge`에 마이그레이션을 마친 뒤, 승인을 받아 한 번 실행합니다.

## 1. 두 가지 구성 비교
| 기준 | 독립형 `--layout independent` (**권장**) | 공유형 `--layout shared` |
| --- | --- | --- |
| 학교 | 가상 학교 5곳(심사위원별) | 가상 학교 1곳 |
| 계정 | 학교마다 1개: 학교 관리자(앱 운영) + 안전업무 담당 | 역할별 5개: 앱 운영담당, 교장, 안전업무 담당, 담임, 교감 |
| 서로 간섭 | **없음**: 학교별 데이터 분리를 그대로 활용, 각자 발령·종료 | 있음: 학교당 진행 중 상황이 1개라 한 사람이 발령하면 모두에게 보이고, 누가 종료하면 다른 사람의 시연도 끝남 |
| 혼자서 전체 흐름 | 가능: 발령 → 대리 보고 → 상황판 → 종료 → 훈련일지 → HWPX | 불가: 역할을 나눠 맡아 함께 진행해야 함 |
| 역할 차이 체험 | 안내서의 권한 대응표로 설명 | 직접 체험 가능 |
| 기존 구조 변경 | 없음 | 없음 |

권장 이유: 심사위원은 각자 다른 시간에 접속할 가능성이 높으므로, 서로 방해하지 않는 것이 가장 중요합니다. 두 구성 모두 같은 스크립트로 만들 수 있습니다. 둘을 함께 쓰려면 독립형을 만든 뒤 공유형을 추가로 실행하세요(slug·이메일이 겹치면 건너뜀).
**주의**: 공유형의 계정 이메일 `judge1~5`는 독립형과 같습니다. 이미 있는 이메일은 건너뛰므로 같은 DB에서 두 구성을 모두 쓰려면 이메일 규칙을 바꿔야 합니다. 현재는 한 가지만 선택하는 것을 전제로 합니다.

## 2. 역할과 기존 권한의 대응(새 권한을 만들지 않음)
| 추천 역할 | 기존 구조 | 할 수 있는 일(`shared/permissions.ts`) |
| --- | --- | --- |
| 앱 운영담당 | 기본 역할 `staff` + 업무 `app_operator` | 교직원 승인·배정, 학급, 소재지, 업무 지정(발령 불가) |
| 교장 | `staff` + 직책 `principal`(운영자 확인 방법에 '가상 시연학교' 기록) | 발령·종료, 상황판, 훈련일지 열람 |
| 안전업무 담당 | `staff` + 업무 `safety_officer` | 발령·종료, 상황판, 훈련일지 작성·수정 |
| 담임교사 | `homeroom` + 1학년 1반 담임 배정 | 배정 학급 보고 |
| 교감 | `staff` + 직책 `vice_principal` | 교장과 같음 |
| (독립형 계정) | `admin` + 업무 `safety_officer` | 위 기능 대부분 + 다른 학급 대리 보고 |

## 3. 만드는 데이터(독립형 기준)
| 항목 | 내용 |
| --- | --- |
| 학교 | `judge-demo-a`~`e`, 이름 'SAFE SCHOOL 심사 시연 A~E초등학교(가상)', `is_demo=true`, 활성. 관할 교육청은 인천·경기·서울·부산·대구(STEP 5 시연용, 실제 소재지 아님) |
| 학급 | 학교마다 1~3학년 × 3반 = 9개, 재적 25명(인원 수만, 학생 정보 없음) |
| 계정 | `judge1~5@judge.safeschool.invalid`(메일이 가지 않는 예약 도메인), 표시 이름 '심사위원 n(가상 …)' |
| 비밀번호 | 무작위 20자(대소문자·숫자·기호). **화면·로그·저장소에 남기지 않고** `--out` 파일(저장소 밖, 새 파일, 권한 600)에만 기록 |
| 직책·업무 | 운영자 기록(`platform_operator`), 확인 방법 '가상 시연학교 — 실제 학교·교직원 아님' |
| 예시 훈련(`--sample-drill`) | 학교마다 지난 화재 모의훈련 1건: 마지막 학급 1개는 미보고, 나머지는 보고(결석 1명) → 종료 → 훈련일지 초안. 기존 서비스 함수(발령·보고·종료·훈련일지)를 그대로 써서 검증 규칙을 거침 |

## 4. 안전장치(스크립트)
- 대상: 배포와 같은 검증. `DEPLOY_PROFILE=production`만 허용하고, Replit 시연·테스트·public 스키마는 거부합니다. 마이그레이션 기록이 없으면 중단합니다(스키마를 만들지 않음).
- 기본은 **계획만 표시**합니다(읽기만). 실제 생성은 `--apply` + `JUDGE_SETUP_CONFIRM=<대상 스키마 이름>`이 있어야 합니다.
- 이미 있는 학교·계정은 건너뜁니다. 기존 계정 비밀번호는 바꾸지 않습니다. 같은 slug가 시연 학교가 아니면 중단합니다. 데이터를 삭제·초기화하지 않습니다.
- 계정을 만들기 전에 비밀번호 파일을 먼저 엽니다(파일 오류로 비밀번호를 잃지 않게).
- 인증 우회 화면·API를 추가하지 않았습니다. 계정은 서버 셸에 접근할 수 있는 운영자만 만들 수 있습니다(기존 `db:seed`와 같은 방식으로 '이메일 확인됨' 표시).

## 5. 작업공간에서 검증한 것 / 못 한 것
| 검증 | 결과 |
| --- | --- |
| 계획·권한·비밀번호·파일·적용 조건 단위 테스트(`tests/step6-deploy.test.ts`) | 대체 실행기 통과 |
| 스크립트 흐름(가짜 Prisma): 설정 없음 / Replit 시연 대상 / 계획 표시 / 마이그레이션 전 / 확인 문구 없음 / 저장소 안 파일 / 정상 생성(공유형) / 같은 파일 재사용 | 8가지 모두 기대대로. 비밀번호는 화면에 0회 출력, 파일 권한 600, DB 비밀번호 비출력 |
| `--sample-drill`(발령·보고·종료·훈련일지 서비스) | **실제 DB 필요 — 미검증.** VPS에서 먼저 시험 스키마(`safeschool_prod_stage`)에 실행해 확인하길 권장 |

## 6. 실행 후 확인
1. `npm run deploy:check`에서 학교 5개·사용자 5명으로 나오는지
2. 계정마다 로그인 → 다른 학교 주소에 접근하면 차단되는지
3. 비밀번호 파일을 전달한 뒤 `shred -u /root/judge-accounts.txt`로 삭제
4. 비밀번호를 다시 발급해야 하면 해당 계정만 운영자 절차로 처리합니다. 별도 도구가 필요하므로 요청해 주세요(이번에는 만들지 않음).
