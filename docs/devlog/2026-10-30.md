## 2. Phase 1-1 상황판 열람 권한과 보고 권한 분리
### 설계 선택과 이유
- 권한을 둘로 나눔: `board.view`(요약, 승인된 교직원 누구나) / `board.detail`(상세, 기존 board.view 보유자 = 관리자·교장·교감·안전업무 담당).
  기존 권한 보유자는 그대로 상세를 보므로 PILOT 1 관리자 화면은 바뀌지 않음.
- 요약 응답은 서버(`restrictBoard`)가 만듦. 학급 메모(학생 이름이 적힐 수 있음)·보고자 이름·부상 인원(학생 건강 정보)·대리 담당 지정 정보는 응답에서 제외 — 화면 숨김에 의존하지 않음.
- 열람 권한은 보고 권한을 만들지 않음: 학급 보고 검사(`submitReport`)는 `board.*` 와 무관하게 학급 배정·대리 지정으로만 판단(관리자 일괄 대리 보고 제거는 Phase 1-3).
- 처음 여는 화면은 `board.detail` 기준으로 바꿔, 담임은 지금처럼 학급 보고 화면에서 시작(요약 상황판은 메뉴에서).
- 상황판 화면의 발령 양식·종료 버튼은 해당 권한자에게만 표시(서버는 원래부터 403).

### 테스트
- 신규 `tests/beta2-board-scope.test.ts`(DB 불필요) 11건 통과: 역할별 권한, 요약 응답에서 민감 항목 제거, 원본 비변경.
- `tests/step7d-isolation.test.ts`에 HTTP 수준 5건 추가(요약 200·민감 항목 없음, 상세 권한자 full, 상황판 열람자 미배정 학급 보고 403, 다른 학교 404) — **DB 필요, 미실행**.
- `tests/step3d.test.ts` 기대값 갱신(담임·교직원 board.view 허용, board.detail 403) — **DB 필요, 미실행**.

## 3. Phase 1-2 상황판 데이터 접근 권한 확정
### 코드 점검 결과
- 승인된 교직원 누구나 부르는 API(학급 목록·진행 중 상황·경보·안내문)에는 학생·교직원 개인 정보 없음.
- 남은 노출 경로: 발령 안내·장소·유형 추가 메모는 자유 입력이며 요약 상황판에 그대로 실림.
- 교직원 소재·대응 가능 여부·미응답자 데이터는 아직 없음(Phase 2). 생길 때 같은 원칙(서버에서 권한별 응답)을 따름.

### 변경
- `shared/personalInfo.ts` 신설: 주민등록번호 형태(서버 거부), 휴대전화번호 형태(화면 경고만 — 공용 비상 연락처일 수 있음). 이름은 형태로 판별할 수 없어 안내 문구로만.
- 발령·발령 수정·유형 추가 스키마에 적용(400 validation_failed). 일반 문구·빈 값은 그대로 통과(기존 요청 호환).
- 발령 화면에 '모든 교직원에게 보인다' 안내와 입력란별 경고, 주민등록번호 형태면 발령 버튼 비활성.
- 요약 응답의 발령 정보도 항목을 하나씩 골라 보냄(사건 정보에 항목이 늘어도 요약에 섞이지 않게).

### 부상 인원 공개(정책 확정 전까지 제한 유지)
- 현재: 일반 교직원 응답에 학급별·학교 합계 모두 없음.
- 검토안(미구현): 학교 합계만 공개하되 합계가 작으면(예: 3명 미만) '있음/없음' 또는 '소수'로만 표시. 학급별 부상 인원은 계속 비공개.

### 테스트
- 순수 함수 4건 추가(개인정보 판별, 스키마 거부·통과, 발령 정보 항목 고정) → 로컬 284건 통과.
- HTTP 7건 추가(업무 없는 교직원·담임 상황판 요약, 종료 상황 요약, 다른 학교 404, 담임 자기 학급 200·다른 학급 403, 일반 교직원 보고·발령·종료·대리 후보 403, 주민등록번호 형태 수정·발령 400) — **DB 필요, CI 미실행**.
