## 2. Phase 1-1 상황판 열람 권한과 보고 권한 분리
### 설계 선택과 이유
- 권한을 둘로 나눔: `board.view`(요약, 승인된 교직원 누구나) / `board.detail`(상세, 기존 board.view 보유자 = 관리자·교장·교감·안전업무 담당).
  기존 권한 보유자는 그대로 상세를 보므로 PILOT 1 관리자 화면은 바뀌지 않음.
- 요약 응답은 서버(`restrictBoard`)가 만듦. 학급 메모(학생 이름이 적힐 수 있음)·보고자 이름·부상 인원(학생 건강 정보)·대리 담당 지정 정보는 응답에서 제외 — 화면 숨김에 의존하지 않음.
- 열람 권한은 보고 권한을 만들지 않음: 학급 보고 검사(`submitReport`)는 `board.*` 와 무관하게 학급 배정·대리 지정으로만 판단(관리자 일괄 대리 보고 제거는 Phase 1-3).
- 처음 여는 화면은 `board.detail` 기준으로 바꿔, 담임은 지금처럼 학급 보고 화면에서 시작(요약 상황판은 메뉴에서).
- 상황판 화면의 발령 양식·종료 버튼은 해당 권한자에게만 표시(서버는 원래부터 403).

## 4. Phase 1-2a 교직원 실명 입력과 학교 관리자의 성명 정정(신규 요구)
### 배경
- PILOT 1 가입 화면은 개인정보 보호를 위해 '닉네임'을 받았음. 재난 대응 시 교직원 확인을 위해 실제 성명으로 전환.

### 구조 감사
- 성명은 `users.display_name` 하나. 모든 화면(상황판 보고자, 대리 담당, 업무 담당, 훈련일지, 안내문)이 요청 시점에 계정 ID로 조회해 표시.
- 보고·수정 이력·감사 기록은 사람을 **계정 ID**로 저장 → 성명을 바꿔도 '누가 했는지'는 유지. 단, 화면 표시는 현재 성명.
- 훈련일지 자동 스냅숏(`auto_snapshot`)은 만들 때의 이름을 JSON으로 고정 보관.
- 한 계정이 여러 학교에 소속될 수 있음(`school_memberships` 학교·사용자 UNIQUE) → 전역 성명을 한 학교 관리자가 바꾸면 다른 학교 화면·기록 표시가 바뀜.

### 설계 선택
- `displayName` 재사용, DB 변경 없음. 새 입력에만 성명 규칙(2~30자, 글자·공백·가운뎃점·하이픈·아포스트로피·마침표, 공백 정리). 기존 계정 이름은 다시 검사하지 않음.
- 성명 정정 권한 `members.rename` 신설 — **학교 관리자만**(앱 운영담당은 승인·배정은 하되 성명은 불가).
- 정정 조건: 같은 학교 승인 교직원, **다른 학교 소속이 전혀 없는 계정**만(있으면 409, 플랫폼 운영자에게 요청), 비밀번호 재확인(10분), 화면에서 본 현재 성명 일치(동시 정정 방지), 사유 필수.
- 성명 외 항목은 요청에서 받지도 않음(스키마가 버림). 감사 기록에 전·후 성명·사유·대상 계정 → 잘못 바꾼 성명도 같은 절차로 되돌림.

### 후속 제안(미구현): 학교별 표시 성명
- `school_memberships.display_name`(NULL 허용, 추가 전용 마이그레이션) — 학교 화면에서는 '학교별 성명 ?? 계정 성명'.
- 다중 소속 교직원도 각 학교 관리자가 자기 학교 표시만 정정. 표시 지점 약 20곳을 학교 문맥 조회로 바꿔야 해 별도 작업 필요.
- 공식 보고서(PDF, Phase 4)에는 작성 시점 성명을 함께 고정 저장 권장.

### 테스트
