# SAFE SCHOOL Beta PILOT 2 — 기술 성과 보고서(포트폴리오)

작성 2026-11-03 · **공개용 문서**: 서버 주소, 계정, 비밀값, 실제 개인정보는 넣지 않았습니다. 세부 근거는 [개발일지](SAFE_SCHOOL_BETA2_개발일지.md)에 있습니다.

> 이 보고서는 코드와 실행 기록으로 확인된 내용만 담습니다. 실제 학교 도입, 실제 재난 알림 전달 성능, 자동 백업의 장기 운영은 아직 검증되지 않았습니다([후속 운영 점검](SAFE_SCHOOL_BETA2_후속운영점검.md)).

## 1. 배경과 학교 현장의 문제

재난이 나면 학교는 학급별 대피 상황을 모으고, 미대피·부상 학생을 확인하고, 관리자와 공유하고, 종료 후 보고서를 작성해야 합니다. 이 과정은 대개 방송, 전화, 메신저, 종이로 나뉘어 있습니다. SAFE SCHOOL은 이 흐름을 하나의 보조 업무시스템으로 잇는 것을 목표로 합니다. 공식 재난 대응 체계나 119 신고, 비상연락망을 대체하지 않는다는 점을 설계 전제로 둡니다.

## 2. 사용자(기획자)가 정한 요구사항

이 프로젝트에서 사용자는 기획, 요구사항 정의, 검증, 운영 의사결정을 맡았고, 구현은 AI와 협업했습니다. 아래는 사용자가 정해 지시한 요구사항입니다.

| 영역 | 요구사항 |
|---|---|
| 데이터 | Beta는 가상 데이터만 사용, 실제 교직원 가입과 개인정보 수집 차단 |
| 보존 | 기존 Prototype 코드는 GitHub에, DB는 암호화 외부 백업으로 보존. 원본 DB는 승인 없이 삭제 금지 |
| 안전 | 서버 상태를 바꾸는 작업은 항목마다 별도 명시 승인. 실패하면 이전 상태로 복귀 |
| 보안 | 비밀번호·해시·접속 문자열·개인키를 출력·저장·공유하지 않음. 추측 접속·인증 우회 금지 |
| 범위 | 이미 통과한 테스트·설치를 반복하지 않음. 원인에 해당하는 최소 수정만 |
| 정직성 | 확인되지 않은 성과를 완료로 적지 않음. 실제 DB 복원 시험 같은 미수행 항목을 구분해 표시 |

## 3. 시스템 구성

```
[브라우저] ─HTTPS─> [Caddy 2.6.2: TLS, HSTS, basicauth, 요청 크기 제한]
                        └─> 127.0.0.1:5100 [SAFE SCHOOL Beta: Express 5 + React 19 정적 화면]
                                              └─> PostgreSQL 16 (Beta 전용 DB·계정·스키마)
                     (종료됨) 127.0.0.1:5000 Prototype — 서비스 중지, DB는 보존
```

- **실행 환경:** systemd 서비스(전용 리눅스 계정, 코드 폴더 읽기 전용, 사진 폴더만 쓰기 허용), cron 일일 백업
- **환경 분리:** 앱이 시작할 때 Prototype의 DB·계정·스키마·포트를 지정하면 실행을 거부합니다(`server/src/deploy/environment.ts`, `server/src/env.ts`).

## 5. 개발·배포 흐름

1. 요구사항과 승인 범위 정의(사용자)
2. 구현과 자동 테스트(AI), 커밋·푸시는 사용자 승인 후
3. GitHub Actions CI 통과 확인
4. 배포 도구 작성 → 로컬 구문·안전성 검사 → 가짜 명령으로 시뮬레이션
5. 사용자가 PowerShell에서 직접 실행. 키 암호와 sudo 비밀번호는 사용자만 입력
6. 실행 기록(비밀값 가림 처리)을 분석해 다음 단계 결정

**서버 상태를 바꾸는 단계는 모두 사용자의 확인 입력을 거칩니다.**

| 단계 | 확인 입력 |
|---|---|
| Caddy 전환 | `SWITCH` |
| 자동 시작·백업 예약 | `FINALIZE` |
| Prototype 종료 | `PROTOSTOP` |
| 과거 백업 삭제 | `PURGE-<개수>` |
| 시험 자원 정리 | `CLEANUP` |
| 가상 계정 재설정 | `RESETDEMO` |

## 6. AI 협업 방식

| 역할 | 담당 |
|---|---|
| 사용자 | 목표·요구사항·금지사항 정의, 운영 결정(Prototype 종료, 백업 위치, 삭제 범위), 실제 서버 실행, 결과 확인과 승인 |
| ChatGPT | 사용자의 단계별 작업 지시문 정리에 활용(사용자 진술) |
| Claude Code | 코드 구현과 테스트, 배포·복구 도구 작성, 로컬 시뮬레이션, 실행 기록 분석과 원인 진단, 문서화 |

- **협업 원칙:** AI는 서버에 직접 접속하지 않았습니다. 키 암호와 sudo 비밀번호가 AI에게 전달되지 않는 구조입니다.
- **오판 사례 1:** AI가 사용자의 "다시 시행"을 재배포로 잘못 이해해 실행 창을 띄웠습니다. 사용자가 정정했고, 이후 지시 없이 실행 창을 띄우지 않는 원칙을 세웠습니다.
- **오판 사례 2:** 서버 시계가 늦다는 판단이 PC 시계 오차 때문이었습니다. 외부 NTP로 다시 측정해 정정했습니다.

## 7. 테스트와 품질 보증

- **앱 코드:** 1,415건의 자동 테스트가 CI에서 통과했습니다. 환경 분리 테스트는 실제 시작 코드를 별도 프로세스로 실행해, 종료 코드와 비밀번호 미출력까지 확인합니다.
- **운영 도구:** CI 밖이므로 따로 3중으로 검증했습니다.
  1. **안전성 정적 검사:** 상태를 바꾸는 줄은 표시가 있고 승인 입력 뒤에 있으며 허용된 줄 수일 때만 통과합니다. Prototype DB와 환경 파일은 읽기 전용 줄에서만 다룹니다.
  2. **시뮬레이션:** 가짜 systemctl·caddy·psql로 정상, 실패, 거부, 강제 종료(kill -9), 연결 끊김 82개 경우를 시험했습니다.
  3. **변형 시험:** 승인 전 변경, 표시 없는 삭제, 삭제 규칙 확대, 시계 강제 변경 등 규칙을 일부러 어긴 사본이 모두 거부되는지 확인했습니다.

## 8. 보안과 개인정보 보호 설계

- **이중 접근 통제:** 공개 주소는 Caddy basicauth(bcrypt 해시만 서버에 저장, 파일 권한 640)와 앱 로그인을 둘 다 거칩니다. 세션 쿠키는 Secure·HttpOnly이고 HSTS를 적용했습니다.
- **실제 데이터 유입 차단:** 가상 데이터 모드(`virtual_test`)에서는 회원가입이 HTTP 503으로 막힙니다. 가상 계정은 메일이 가지 않는 예약 도메인을 씁니다.
- **비밀값 처리:**
  - 비밀번호는 명령 인자로 넘기지 않고 표준 입력으로만 전달합니다.
  - 화면과 기록에는 가림 처리를 적용합니다.
  - 해시도 출력하지 않습니다.
- **백업 보호:** Prototype 실제 데이터는 RAM 디스크에서만 평문으로 다룹니다. AES-256으로 암호화한 뒤 서버와 PC 양쪽에서 복호화를 확인했고, 서버 임시 파일은 shred로 지웠습니다. 서버에 쌓여 있던 과거 백업은 승인을 받은 뒤 정해진 이름 규칙에 맞는 파일만 파기했습니다.
- **실제 사고와 대응:** 초기 점검 스크립트의 가림 결함으로 DB 비밀번호가 사용자 터미널에 노출됐습니다. 결과 파일에서 값을 지우고 스크립트를 삭제한 뒤, 이후 도구는 출력 구조 자체를 바꿨습니다. 비밀번호 교체는 사용자 결정으로 보류 중입니다.

## 9. 배포 장애 분석과 해결

| 문제 | 원인 | 해결 | 검증 |
|---|---|---|---|
| 설치 90% 실패 | 테이블 이름 추정(`school_classes`), 실제는 `@@map("classes")` | Prisma 스키마와 대조, 전체 테이블 비교 | 40개 테이블 백업·복원 비교 통과 |
| 전환 사전 로그인 401 | 설치를 다시 실행할 때 시드가 해시를 덮어씀 → 비밀번호 불일치 | 가상 계정 5개의 해시만 재설정(대상·DB를 트랜잭션 안에서 재확인) | 내부 로그인 200 |
| Caddy 해시 형식 오류 | v2.6.2는 bcrypt 원문 출력, 도구는 base64 기대(가짜 객체도 틀림) | 실제 형식을 엄격히 검사 | 정상 4종 통과, 비정상 9종 거부 |
| 연결이 끊기면 복귀 실패 가능 | 끊긴 화면에 출력하다 스크립트가 먼저 종료 | 끊기면 출력을 서버 기록으로 돌린 뒤 복귀, 10분 자동 복귀 예약 추가 | kill -9·연결 끊김 시뮬레이션 |
| 명령줄 길이 한도 | 서버 스크립트 증가 | gzip 압축 후 전송 | 압축 왕복 후 원본과 동일 |
| 시계 오차 오판 | 장비끼리 상대 비교 | 외부 NTP 직접 질의 | 서버 오차 0.01초, 변경 불필요 |

## 10. 운영 자동화와 백업·복구 전략

- **자동 복귀:** 검증에 실패하면 즉시 사본으로 복귀합니다. 세션이 끊겨도 서버 예약이 10분 안에 스스로 복귀시킵니다.
- **수동 복귀:** 도구로 `ProtoStart` → `Rollback`을 실행하고, 도구를 쓸 수 없으면 SSH 수동 절차 문서를 따릅니다.
- **백업:**
  - Beta: 매일 03:50(KST) 덤프와 사진 묶음, 14일 보관
  - Prototype: 암호화 사본을 승인된 PC 폴더에 보관
- **점검:** 읽기 전용 `Inspect` 하나로 연결, 서비스, 예약, 백업 목록, 시계 동기화를 함께 확인합니다.
